1. OTP EXPIRY, ONE-TIME USE, RESEND LIMITS & RATE LIMITING
================================================================================

A. Cryptographic Token Hashing at Rest:
   - Generated 6-digit numeric OTPs (crypto.randomInt(100000, 1000000)) are
     hashed using SHA-256 before database insertion. Plaintext tokens are never
     persisted at rest in PostgreSQL.
   - Endpoint: POST /api/auth/forgot-password & POST /api/auth/reset-password

B. Strict Expiration Window:
   - Tokens carry an explicit expiresAt timestamp set to exactly 15 minutes
     from generation (new Date(Date.now() + 15 * 60 * 1000)).
   - The password reset handler enforces this check: if new Date() > expiresAt,
     the request is rejected with 400 Bad Request ("Password reset token has expired").

C. Atomic One-Time Verification:
   - The reset flow executes inside a Prisma database $transaction that marks
     the token as used: true concurrently with updating passwordHash.
   - Subsequent attempts to reuse the same token are rejected with 400 Bad Request
     ("Invalid or already used password reset token").

D. Previous Token Invalidation:
   - Requesting a new OTP via POST /api/auth/forgot-password executes an atomic
     updateMany query marking all existing unused reset tokens for that user
     as used: true, preventing race conditions or replay attacks.

E. Session Revocation on Password Reset:
   - Successful reset atomically increments user.tokenVersion ({ increment: 1 }).
     This immediately revokes all active JWT sessions across all devices.

F. Account Enumeration Defense:
   - POST /api/auth/forgot-password returns a generic 200 OK success message even
     if the requested email does not exist in the database, preventing attackers
     from enumerating valid registered user accounts.

G. OTP Resend Cooldown & Rolling Hourly Cap:
   - 60-Second Cooldown: Enforces a minimum 60-second gap between consecutive OTP
     requests for the same user across all verification channels.
   - 5 Resends / Rolling Hour: Limits users to a maximum of 5 OTP generation
     requests per rolling 60-minute window to mitigate SMS/email flooding.
   - HTTP 429 Status Code: Returns 429 Too Many Requests with standard Retry-After
     header indicating remaining cooldown seconds.
   - Protected Endpoints:
     * POST /api/auth/forgot-password
     * POST /api/auth/verify-email/send
     * POST /api/auth/verify-phone/send

H. Failed Attempt Counter & Account Lockout (3 Strikes):
   - Database Tracking: Tracked via failedAttempts Int @default(0) on the
     PasswordResetToken model.
   - Lockout Enforcement: Each incorrect code increments the counter. Upon reaching
     3 failed attempts (MAX_FAILED_ATTEMPTS = 3), the active token is permanently
     locked and invalidated (used: true).
   - HTTP 429 Invalidation: Returns 429 Too Many Requests ("Too many incorrect
     attempts. This code has been invalidated. Please request a new code.") once
     locked.
   - Protected Endpoints:
     * POST /api/auth/reset-password
     * POST /api/auth/verify-email/confirm
     * POST /api/auth/verify-phone/confirm

2. DEVELOPMENT AUTHENTICATION BYPASS (x-user-id) STATUS
================================================================================

- Confirmation: The x-user-id development bypass header has been COMPLETELY
  REMOVED / ELIMINATED from the codebase.
- File Verified: src/lib/auth-guard.ts
- Authentication Policy:
  1. Every protected endpoint strictly requires a valid HTTP header:
     Authorization: Bearer <token>
  2. Tokens must be cryptographically signed via HMAC-SHA256 (HS256) matching
     the server JWT_SECRET.
  3. The database user must exist and have accountStatus !== "SUSPENDED".
  4. The token's embedded tokenVersion claim must match user.tokenVersion in
     PostgreSQL. Any discrepancy (due to logout, suspension, or password change)
     causes immediate rejection with 401 Unauthorized.
